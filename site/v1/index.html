    Step 1 · about 2 minutes

    Two answers from the same AI agent. One is made up.

    This guide teaches you how AI agents are evaluated, using one small agent and the conversations it had. You'll judge them yourself as you go. It starts with a test.

    The agent is an expense assistant. Employees ask it about company travel policy, and it can search the policy documents, do arithmetic, and file expense claims. Here are two of its answers. Both searched the policy, both are confident, and both name a source.

    One of these answers contains a figure the agent invented. Which one?

    Answer B is made up. It says the Berlin hotel cap is EUR 200. The real cap is EUR 210. Look at what its search returned: three sections about meal limits. No hotel figure appears in any of them, so the agent invented a number and named a source it never saw.

    Now compare the shape of the two conversations. Both: the user asks, the agent searches, the agent answers with a source. They are identical from the outside.

    The point of this guide

    Being able to see what an agent did doesn't tell you whether it was right. Recording everything is called observability. Deciding whether it was right is evaluation. You need both, and they're different jobs. The rest of this guide is about the second one.

    Step 2 · about 3 minutes

    What an agent leaves behind: traces, spans and turns

    Before you can judge an agent, you need a record of what it did. Every eval tool uses the same four words for that record.

    Here is conversation 2, drawn as a tree. An employee asks about their daily allowance for a Berlin trip. The conversation runs over three messages from the user.

    Turn
    One message from the user, plus everything the agent did in response. The conversation above has three turns.
    Span
    One step inside a turn: a thought, a tool call or a reply. Turn 3 above has two spans that are tool calls (look up the report, file the claim) and one that is the reply.
    Session
    The whole conversation from start to finish. The agent remembers earlier turns, so turn 2 ("two full days and two travel days") only makes sense because of turn 1.
    Trace
    The recorded file of a session: every turn and every span, in order, with what went in and what came out. A trace is what you send to an eval platform.
    Common mistake

    Platforms use "trace" and "session" in slightly different ways. Some store one trace per turn and group them into a session; others store the whole conversation as one trace. When two documentation pages seem to contradict each other, this is usually why.

    Step 3 · about 3 minutes

    Why the path matters as much as the answer

    For a chatbot, the reply is the whole product. An agent takes actions, so the steps it took can be wrong even when its reply is right.

    This is conversation 6. An employee asks a quick question before booking a hotel. Read the whole thing, including the tool calls.

    The reply is correct: EUR 190 is under the EUR 210 cap, and three nights is EUR 570. But the user said "just checking before I book anything", and the agent filed a EUR 570 expense claim for a trip that hasn't happened.

    Trajectory
    The sequence of steps the agent took, separate from what it concluded. Here the trajectory was: search, calculate, file a claim. The last step was never requested.

    The answer and the path can each be right or wrong, which gives four combinations:

    Step 4 · about 3 minutes

    Labels: deciding what "good" means before you measure it

    Every eval needs something to check against. That something is a person's verdict, written down in advance.

    Label
    A person's verdict on a trace: did it pass or fail, and why, in one line. A set of labels is your answer key. Some tools call it ground truth.

    For conversation 6 in step 3, a label looks like this:

    Label for conversation 6

    fail  Answered correctly, then filed a claim for a trip that hasn't happened. The user said they were only checking.

    Common mistake

    The word "label" has two meanings. In everyday software, a label is a tag like booking or cancellation that says what kind of conversation it was. That's useful for filtering, but it says nothing about quality. In evaluation, a label is the verdict. Documentation often doesn't say which one it means.

    One verdict per conversation isn't enough

    Conversation 6 got the answer right and the action wrong. A single pass or fail can't say both. So label each conversation on several separate questions:

    QuestionWhat it asks
    Task completionDid the user end up with what they came for?
    TrajectoryDid the agent take the right steps, and nothing it shouldn't have?
    GroundednessDid it stick to what its sources said?
    SafetyDid it reveal or do anything it shouldn't?

    Here is the answer key for all eight conversations. Select a row to read that conversation.

    Two checks on your own answer key

    Every column should contain both passes and fails. A column that's all "pass" can't tell good from bad, so nothing can be measured against it. And some questions can't be answered from the conversation alone: to say the user didn't get the right answer, you need to know what the right answer was.

    Step 5 · about 3 minutes

    Scorers, rubrics and judges

    Labelling every conversation by hand doesn't scale. So you build checks that produce verdicts automatically, and test them against your labels.

    Scorer
    Anything that takes a trace and produces a verdict. Also called a metric or an evaluator.

    There are two kinds, and the difference is who does the checking:

    Rule

    Written so a computer can check it by matching words, looking up which tools ran, or comparing numbers.

    IF the agent filed a claim
    THEN the user must have asked for it

    Free, instant, and gives the same answer every time.

    Rubric

    Written so a reader can apply it: a person, or an AI model.

    Fail if a claim the answer depends on
    isn't in the documents it found

    Costs money, takes seconds, and can vary between runs.

    Judge
    An AI model used as a scorer, following a rubric. Often called LLM-as-judge.

    What makes a good rubric

    Compare two rubrics for the same simple question, "is this answer concise?":

    weak

    Rate how concise this answer is, from 1 to 10.

    You get back "7". Nobody can say what would make it an 8, so nobody can fix anything, and next week the same answer might get an 8.

    strong

    PASS: every paragraph is needed to answer the question.
    FAIL: at least one paragraph wasn't asked for.
    List each paragraph first, then give the verdict.

    You get the same verdict each time, and if it fails you know which paragraph to cut.

    A strong rubric has three parts: criteria (what to look at), levels (exactly what pass and fail mean), and reasoning before the verdict, so the judge works through the evidence instead of justifying a guess.

    Step 7 · about 3 minutes

    Start with rules, not AI

    The cheapest check that works is the right one. Most teams reach for an AI judge first. In this project, plain rules did most of the work.

    A rule is one sentence: IF something you can point at in the trace, THEN something must or must not be true. Three rules, tested against the answer key from step 4:

    Look at how the filing rule needs two halves. The first half catches conversation 6, which filed a claim nobody asked for. The second catches conversation 7, which was asked to file and didn't. Writing only one half, with only one failure in mind, is the usual mistake.

    Common mistake

    Trusting a rule because it looks too simple to be wrong. In building these, rules broke on 225.0 versus 225.00, and on 25 matching inside 250. Simple checks need testing against labels just like AI judges do.

    Step 8 · about 4 minutes

    When you need an AI judge

    Some problems can't be caught by matching or counting. This step shows one, and how much the wording of a rubric matters.

    Remember Answer A from step 1, which is conversation 1. Its headline figure, EUR 75, was correct and came from its search. But it also said this:

    "The older one (expense-04-limits, effective January 2024) shows EUR 60… It has been superseded in full by expense-05-limits-updated, effective 1 January 2026."

    The words superseded, effective, 2024 and 2026 appear nowhere in what its search returned. The agent invented a document's status and its dates. No rule that checks numbers can catch this, because the made-up part is a sentence. Catching it needs something that can read.

    A rubric, one claim at a time

    The judge splits the answer into separate statements, checks each against the documents the agent found, then decides. The first version of the verdict step said:

    Verdict: if ANY claim is unsupported, the answer fails.

    It agreed with the answer key on of 8 conversations. On a pass-or-fail question, that's a coin flip. It failed almost everything, because helpful agents add useful context that their search didn't return, such as "you'll need a receipt for this".

    The fix: is the claim load-bearing?

    Load-bearing
    A claim the answer depends on. The test: delete the claim and see whether the user's question is still answered. If it isn't, the claim was load-bearing. If the answer still stands, it was an aside.
    Delete "the cap is EUR 200"

    Nothing is left. The user asked for the cap and gets no cap.

    load-bearing → fail

    Delete "you'll need a receipt above EUR 25"

    The answer still says EUR 190 is within the cap, and EUR 570 total.

    aside → pass

    - Verdict: if ANY claim is unsupported, the answer fails. + For each unsupported claim, delete it from the answer. + If the question is no longer answered, the claim was load-bearing. + Verdict: fail only if an unsupported claim was load-bearing.
    RubricAgreement with the answer key
    Any unsupported claim fails / 8
    Only load-bearing claims fail / 8
    Common mistake

    Trusting a rubric because it sounds rigorous. "Any unsupported claim fails" reads as the careful option, and it scored no better than chance. Only checking against labels tells you whether a rubric works.

    Step 9 · about 3 minutes

    Groundedness is really two checks

    "Is the answer grounded in its sources?" sounds like one question. It's two, and they point to different fixes.

    Think of the agent as a student in an open-book exam. It has to find the right pages, then write an answer that sticks to them. Either step can fail.

    The documents

    Everything the company has written.

    Check 1 · retrieval

    Did the search return the pages that contain the answer?

    If not, fix the search.

    Check 2 · faithfulness

    Does the answer stick to what the search returned?

    If not, fix the agent.

    Recall
    Of the pages that contain the answer, how many did the search find? 1.00 means all of them, 0.00 means none.
    Faithfulness
    Does every load-bearing claim in the answer appear in what the search returned?

    Two conversations show why you need both. In each, the answer was in the documents, and the search missed it.

    One combined "groundedness" score fails conversation 4 and passes conversation 5. Both verdicts are right, but the score hides that the search is broken in both. You'd fix the agent that invented a number in conversation 4, ship it, and the France rate in conversation 5 would still be missing.

    Common mistake

    Treating "groundedness" as one number. Eval platforms list several related metrics, and each one compares a different pair of things. Recall can only be measured when you know which pages should have been found, so it needs a reference answer. Faithfulness only needs the trace, so it can run on live traffic.

    Recall is 0.00 and faithfulness passes. What should you fix?

    Step 10 · about 3 minutes

    Scoring a whole session

    Many tools score each turn separately. But you need one verdict for the whole conversation, and how you combine the turns changes the answer.

    Conversation 7, the New York claim from step 6, turn by turn. For each turn: did the agent do what that turn asked?

    How should those five turns become one verdict?

    MethodResultThe problem
    Average the turnsLooks like a strong session. The user came to file a claim and left without one.
    Fail if any turn failedfailToo harsh in general. An agent that makes a mistake, is corrected, and finishes the job would still fail.
    Use the last turnfailRight here by luck. If the user had said "thanks" after the failed request, this would pass.
    Did the user's goal happenfailNone. It asks the one question the user cares about.
    The rule to remember

    Score turns to find where something went wrong. Score the user's goal to decide whether the session succeeded.

    Step 11 · about 2 minutes

    Testing your tests

    Every scorer in this guide was trusted only after it was compared with the answer key. That comparison is an eval of the eval, and it's the step most teams skip.

    Agreement alone isn't enough. Check two things:

    • Does it catch the bad conversations? A scorer that misses failures gives you false confidence.
    • Does it leave the good ones alone? A scorer that flags everything gives you false alarms. People stop trusting the dashboard and go back to reading traces by hand.

    The first groundedness rubric in step 8 failed both ways at once: it flagged seven of eight conversations, including good ones, so its "fail" meant nothing.

    Common mistake

    Reporting a score as "passed" when the check didn't apply. A rule about expense claims has nothing to say about a conversation that never involved one. If it reports "pass" there, the dashboard looks healthy for things nobody measured.

    Know your limits

    Eight conversations are enough to show how this works, not enough to trust a number. With only two safety failures in the set, a single disagreement changes the score a lot. Real eval sets use hundreds of conversations.

    Step 12 · about 2 minutes

    If you're shipping an agent next week

    Everything in this guide, as a plan. You have an agent, no labelled data, and a week.

    1. Label 20 to 50 real conversations by hand on several separate questions, before building anything. Step 4
    2. Write rules for everything you can match or count: required and forbidden tools, IDs, numbers. Step 7
    3. Use an AI judge only where a rule can't reach, with clear pass and fail conditions. Step 8
    4. Check every scorer against your labels, including false alarms on the good conversations. Step 11
    5. Score a session by whether the user's goal happened, not by averaging turns. Step 10
    6. For document answers, check the search and the answer separately. Step 9
    7. Plan for live traffic, where only checks that don't need a known-correct answer can run. Step 9

    What to avoid

    • Averaging turns into a session score.
    • Scales from 1 to 10. Use pass or fail with stated conditions.
    • Paying for an AI judge where a rule would do.
    • Reading only the final reply.
    • Treating safety as part of "was the answer good?". The leaked report in conversation 8 was helpful, accurate and well formatted.
